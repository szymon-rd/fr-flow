# Changing a core type

This procedure is for changing a type that several packages or modules use:
`Node`, `KnowledgeBase`, `Term`, `SnapNode`, `Overview`, `Review`, `Decision`
and others like them. A small change inside one package needs only steps 1, 6,
7 and 8.

The order matters. The theory and the types are decided before code because
they are cheap to change while they are on paper, and expensive once forty
files depend on them. Behaviour is pinned before anything moves, so every later
step can be checked against it.

## 1. Baseline

Start from a clean tree on the branch you will commit to.

```sh
sbt test                       # must be green
sbt leanTest                   # when the change can affect generated Lean or proofs (minutes)
python3 -I .claude/skills/scala-fp/references/measure.py > "$BASE/measure.txt"
```

`$BASE` is a directory in your scratchpad. Record the outputs users see for
every example project in `build.sbt` (`auth`, `crm`, `keycloak`, `sharing`; `scale` is generated by `bench/generate.py`):

```sh
for ex in auth crm keycloak sharing; do
  bin/frflow $ex render > "$BASE/$ex.render.txt" 2>&1
  cp -r examples/$ex/lean/FrFlowGen "$BASE/$ex.lean"          # the generated Lean
  cp examples/$ex/.frflow/kb.json "$BASE/$ex.kb.json"         # the snapshot
  for c in tree inbox status; do bin/frflow $ex $c --json > "$BASE/$ex.$c.json" 2>&1; done
done
```

The CLI golden files in `modules/cli/src/test/resources/golden` are checked by
`sbt test`. If the type you change has a JSON form that is written to disk
(snapshot, ledger, reviews), record a file written by the current code. That
file must still be readable after the change.

## 2. Theory first

Write a short note, a page at most, in domain words:

- **What the concept is**, in two sentences, without "and".
- **Its cases**: the kinds of value it has, each with its own data. A case that
  has no data of its own and no behaviour of its own is not a case.
- **Its operations and their laws**: what every user of the type needs, as
  signatures with a sentence each, and the laws (equations or properties) they
  obey.
- **What it is not responsible for**: the interpreters (printing, running,
  checking, persistence, display) and the configuration that belongs to them.
  Name the package each one moves to.
- **Its relations**: what it refers to, by id or by value, and what refers to
  it. Edges between instances (parents, replaces, keeps) are often a concept of
  their own.

Present the note to the owner and wait for approval. Do not write code that
depends on an unapproved theory.

## 3. Types before code

Write the new types and the signatures of their operations, with `???` bodies,
in a scratch file or in the PR description. Add a table that maps each old field
and method to its new place:

| Old | New | Reason |
|---|---|---|
| `Node.kind: NodeKind` | the `Node` case | D1, D3 |
| `Node.isInvariant` | deleted, it is `case Invariant` | D3 |
| `Node.governs: List[String]` | `Design.governs: NonEmptyList[RelPath]` | D4, D6 |
| `Node.runCheck` | `runtime.RunPlan.checks` | B5 |
| `Node.enforce` | `runtime.Enforce.wrap` | B2 |

Every old field appears in the table. "Deleted" is a valid destination if the
reason is given. Present the types and the table for approval.

## 4. One concept per change

Each commit changes one concept and what directly depends on it. Do not combine
the change with renames elsewhere, formatting, or a second concept. If you find
another problem on the way, note it and leave it for its own change.

A large type can be split over several commits, each green. For example: first
extract `Statement`, then move the interpreters out, then turn the class into
an enum.

## 5. Delete before add

Before you introduce the new types, remove what the theory has no place for:

- fields that are never read (`grep` each field name across `modules` and
  `examples`);
- state that duplicates other state (`isInvariant` next to `kind`);
- features with no user in the examples, the docs or the owner's plans: ask the
  owner before deleting a feature;
- adapters and compatibility shims left from earlier changes.

Run the tests after each deletion. A smaller type is easier to move.

## 6. Let the compiler drive

Change the type, then fix the compile errors outward, module by module in
dependency order (`protocol`, `model`, `lean`, `ledger`, `check`, `api`, `cli`,
`web`, `agent`, then `examples`). Do not add a conversion or adapter that keeps
the old shape alive so that callers can stay unchanged. If an adapter is needed
to keep a commit green, it is removed in the next commit of the same series.

Keep `-Werror` on. Do not add `@nowarn` to get through a migration.

## 7. Behaviour preserved

Run the baseline commands again and compare:

```sh
sbt test && sbt leanTest
for ex in auth crm keycloak sharing; do
  bin/frflow $ex render > "$NEW/$ex.render.txt" 2>&1
  diff -r "$BASE/$ex.lean" examples/$ex/lean/FrFlowGen
  diff "$BASE/$ex.kb.json" examples/$ex/.frflow/kb.json
  for c in tree inbox status; do bin/frflow $ex $c --json | diff "$BASE/$ex.$c.json" -; done
done
```

Generated Lean, CLI output and `--json` output are identical unless a
difference was planned in step 3. List every planned difference, with its
reason, for the owner. A change to the snapshot's JSON shape is a protocol
change: old files must still decode, or the change says how they are migrated.

Add the property tests for the laws stated in step 2 (X1), and keep them.

## 8. Re-measure and describe

```sh
python3 -I .claude/skills/scala-fp/references/measure.py > "$NEW/measure.txt"
diff "$BASE/measure.txt" "$NEW/measure.txt"
```

The files you touched have no new budget violations, and the type you changed
is within budget. The commit message says which concept changed, which rules
the change satisfies, and what was deleted.

## Worked plan: `Node`

This is a starting point for step 2. It is not an approved design.

**Findings it resolves.** `Node` (`modules/model/src/main/scala/frflow/node/Node.scala`)
has 24 fields for six kinds (D1). `kind` and `isInvariant` say the same thing
(D3). The builders reject illegal combinations with `require` (D2, F8).
`governs` and `file` are paths held as strings, and `at = -1` and
`ideaSection = ""` are sentinels (D4, D5). Run-time configuration
(`runCheck`) is stored on the statement (B5). The file runs examples
(`checkExamples`) and wraps implementations (`enforce`), and imports `example`
and `runtime` to do it (B2, B3). `enforce` does about eight jobs (F1). `Keep`
is a union written as an `Option` plus a string (D1).

**A possible theory.**

- A *node* is one statement the developer decided, in their words, of one of
  six kinds: claim, invariant, contract, assumption, definition or design.
  Each kind carries what it states: a formula, a rule over pairs, a post on an
  operation, a trusted fact, terms it fixes, or files it governs.
- A *refinement* is the graph between nodes. A node rests on the nodes it is
  `under` and on the invariants it keeps. It may replace one alternative. Laws:
  the graph is acyclic, a definition has no parents, and a node rests on every
  invariant it keeps.
- *Evidence* attached to a contract (examples and expected consequences) is data
  about the contract. It is checked by `frflow.example`.
- *How a contract runs* (check every call, sampled, or never, and where
  violations go) is a `RunPlan` in `frflow.runtime`. It is not part of the node.

**Possible types (step 3).**

```scala
final case class Statement(id: NodeId, text: String, why: String, idea: Option[IdeaSection], at: Option[SourcePos])

enum Node:
  case Claim(about: Statement, formula: Lifted[Boolean])
  case Invariant(about: Statement, rule: Rule, scope: List[NodeId])
  case Contract(about: Statement, op: Operation, post: Post, check: Option[Check], onFailure: Option[FailureClause],
      fixes: Fixes)
  case Assumption(about: Statement, trusted: Trusted)
  case Definition(about: Statement, terms: NonEmptyList[Subst])
  case Design(about: Statement, governs: NonEmptyList[RelPath])

enum Keeping:
  case Kept(invariant: NodeId, view: View)
  case Exempt(invariant: NodeId, because: String)

final case class Refinement(under: Map[NodeId, NonEmptyList[NodeId]], replaces: Map[NodeId, NodeId],
    keeps: Map[NodeId, List[Keeping]])
final case class Evidence(examples: Map[NodeId, List[Example]], expects: Map[NodeId, List[Expectation]])
```

`Contract` has six fields, within budget. If the DSL needs the operation's type
`F` for typed examples, `Contract[F]` becomes a type parameter of that case
only, and the other cases stay unparameterised. Whether the DSL builders
return the case directly (S2), and how `under` and `keeps` record edges, are
decisions for the owner in step 2.

**Order of commits.**

1. Delete: `isInvariant` and `shownKind` (render the case in `cli`), and any
   field `grep` shows unused.
2. Move `checkExamples` and `postFn` to `frflow.example`, and `enforce` (split
   per F1) to `frflow.runtime`. `Node.scala` no longer imports either package.
3. Replace `Keep` with `Keeping`.
4. Introduce `Statement`, `RelPath` and `SourcePos`, and remove the sentinels.
5. Move `runCheck` to `RunPlan`.
6. Turn `Node` into the enum, with builders returning the cases. Move the edges
   to `Refinement` if the owner chose that in step 2.
7. Rebuild `SnapNode` as a header plus `SnapBody`, derived by
   `Snapshots.node` (V1, V2). This changes the snapshot's JSON, so it is a
   protocol change (step 7).

Each commit passes steps 6 to 8 on its own.
