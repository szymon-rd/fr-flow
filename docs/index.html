    FrFlow documentation

    FrFlow is a method and a tool for building software with AI agents without losing track of what the software is for. The agent writes the code and a tree of small statements that explain it. Lean proves that the statements fit together and that the code meets them. You decide every statement, and you see it again when it changes.

    FrFlow is written in Scala 3 and uses Lean 4. This page has four kinds of section, marked next to each heading: a tutorial to learn it, how-to guides for tasks, the reference, and explanations of why it works as it does. For an overview, read the README.

    FrFlow is in two layers. FrFlow (core), every section up to With an AI agent, is the method and its tools: the DAG, the proofs, the decisions, the CLI and the web view, which a developer uses with no AI. With an AI agent is a layer on top, which a project enables: an agent proposes the nodes and writes the code and proofs, and the developer asks it for changes.

    • New to FrFlow: start with Get started, then the tutorial.
    • Writing a model: see Terms and Nodes.
    • Using the command line: see Commands.
    • Working with an AI agent: see With an AI agent.
    • A check failed: see Troubleshooting.

    Why FrFlow Explanation

    Using AI agents for coding brings two problems:

    • Lost Theory. Peter Naur argued that a program is the visible part of a theory its programmers hold: why it is built the way it is, and how it maps to the world. When agents write the code, nobody on the team builds that theory, and the agent loses it when its context ends.
    • Drift. Each change an agent makes can move what the system does a little away from what was intended. Each step looks reasonable on its own, and a reviewer of a large diff has no record of the intent to compare against.

    FrFlow addresses them with a formal refinement flow:

    1. IDEA.md says the purpose of the system, in prose. You accept it. With the agent layer, you tell the agent your idea in chat; it asks what it needs, records the conversation, and writes IDEA.md from it.
    2. A root states the purpose exactly, in one statement: both what users can do and what must never happen.
    3. The root is refined into parts, in your domain's words: claims, contracts on operations, assumptions, definitions of terms, and design decisions. Parts have parts, down to the code. The result is a DAG.
    4. FrFlow translates the DAG to Lean and proves that the parts of each node imply it, that the code meets its contract, and that the root follows from the code and a short list of trusted assumptions.
    5. You accept or reject each node, in the terminal or in a local web view. Each decision is signed and kept in a ledger with your reason.
    6. When something changes, every node it affects comes back for review, with a diff.

    The theory is written down, one sentence and one why per node; the links between the statements are proven; and drift shows up as a node back in your queue. This costs work: you read and decide nodes, and the agent writes proofs. That work goes where using AI is risky: the intent, and whether the code still matches it.

    Tutorial: read a knowledge base, top to bottom Tutorial

    This walks through examples/auth in the order it is written and decided. Every snippet is the example's code. Open examples/auth/src/main/scala/auth/Auth.scala beside this page.

    1. The idea

    The purpose is in IDEA.md: a title, a lead paragraph, sections, and what is not modelled. In a new project you write it, or the agent writes it from your conversation, and you accept it (Start a project); this example's is accepted as it stands.

    examples/auth/IDEA.md
    # Auth

A system decides which users may access which resources. No user may ever
access a resource they are not authorized to access.

Users identify themselves with tokens they receive at login. Authorization is
given by a table of grants: a user may access a path when a grant names that
user and that path.

## Not modelled

- How tokens are issued at login, and when they expire.
- Who may change the table of grants.

    2. Open terms

    The root speaks in the idea's most general words. An Opaque is a domain type that is not fixed yet; a Param is a term: a fact of the world or an operation of the system. Each says what it means.

    val User       = Opaque("User", "a person who uses the system")
val Resource   = Opaque("Resource", "something a user may want to access")
val access     = Param[(User.T, Resource.T) => Boolean]("access", "whether the system lets the user access the resource")
val authorized = Param[(User.T, Resource.T) => Boolean]("authorized", "whether the user is allowed the resource, by whatever rule the system adopts")
val signedIn   = Param[User.T => Boolean]("signedIn", "whether the user has signed in, so can present who they are")

    3. The root

    The root states the purpose exactly: access holds exactly when the user is signed in and authorized. The sentence is what you decide; the formula is what Lean reads. Formulas are written with terms: lambdas over Term[…], compared with ===.

    val accessExactly = Node.claim("AccessExactly",
  "A user gets access to a resource exactly when they are signed in and authorized for it.",
  why = "The idea says no one may access what they are not authorized to; and authorization is what lets a signed-in user in, or the system would serve no one. Who is authorized, and how a user signs in, the domain says below."
)(forall((u: Term[User.T], r: Term[Resource.T]) => access(u, r) === (signedIn(u) && authorized(u, r))))

    4. The domain, by definitions

    Below the root, definitions bring in the domain: users are ids, resources are paths, and the open terms get their meaning from tables. A case class that formulas build from terms has a companion that extends Data.

    final case class UserId(name: String)
final case class Path(value: String)
final case class Grant(user: UserId, path: Path)
object Grant extends Data[Grant]

val grants   = Param[List[Grant]]("grants", "the grant table as stored when the request is decided")
val sessions = Param[String => Option[UserId]]("sessions", "the session table as stored when the request is decided: a token to the user it was issued to at login")
val admit    = Param[(String, Path) => Option[UserId]]("admit", "the system's decision on a request (a token and a path): the user it is admitted on behalf of, if any")

val identities = Node.definition("Identities", "Users are named by ids, and resources are paths.",
  why = "The grant table names users by id and resources by path, so these are what the system knows them by."
)(User := of[UserId], Resource := of[Path])

val grantTable = Node.definition("GrantTable", "A user is authorized for a path when a grant names that user and that path.",
  why = "The idea defines authorization as a table of grants; who may change the table is not modelled."
)(authorized := ((u: Term[UserId], p: Term[Path]) => grants.contains(Grant(u, p))))

val sessionTable = Node.definition("SessionTable", "A user is signed in when some session token was issued to them.",
  why = "Users identify themselves with tokens they receive at login; the session table records which token was issued to whom. How tokens are issued is not modelled."
)(signedIn := ((u: Term[UserId]) => exists((t: Term[String]) => sessions(t) === Some(u))))

    5. The parts

    The root has three parts. Lean proves that together they imply it (complete), and tries to show that each one is needed. This is the capability part: a granted user gets in.

    val grantLetsIn = Node.claim("GrantLetsIn",
  "A request whose token was issued to a user with a grant for the path is admitted on their behalf.",
  why = "A grant is there to be used: a system that turned a granted user away would meet the rules by serving no one."
)(forall((t: Term[String], p: Term[Path]) => sessions(t).forall(u => grants.contains(Grant(u, p)) ==> (admit(t, p) === Some(u))))).under(accessExactly)

    6. A contract, with examples

    A contract states, for one call of an operation, what every result must satisfy, so each result of the running system can be checked. Examples are concrete calls: an expect the contract must allow and a reject it must refuse. Lean evaluates them too, and must agree with Scala.

    val decisionContract = Node.contract(admit)("DecisionContract",
  "A request is admitted on behalf of the user its token was issued to, exactly when a grant names that user and the path.",
  why = "The three parts, stated for one call, so every result of the running system can be checked."
)((token, path, decision) => decision.forall(u => sessions(token) === Some(u) && grants.contains(Grant(u, path))) &&
  sessions(token).forall(u => grants.contains(Grant(u, path)) ==> (decision === Some(u))))
  .under(tokenNamesHolder, accessNeedsGrant, grantLetsIn)
  .examples(grants.bind(List(Grant(UserId("alice"), Path("/a")))), sessions.bindTable(Map("t1" -> UserId("alice"))))(
    expect("t1", Path("/a"), Some(UserId("alice")), "Alice's token and a grant for /a: she gets in"),
    expect("t1", Path("/b"), None, "no grant for /b: refused"),
    reject("t1", Path("/b"), Some(UserId("alice")), "access without a grant is never given"),
    reject("t2", Path("/a"), Some(UserId("alice")), "a token that is not Alice's never acts for her"),
    reject("t1", Path("/a"), None, "Alice with a grant for /a is not turned away"))

    7. The code, tested against the contract

    The decision is plain Scala. The proofs above rest on DecisionContract alone; check tests this code against it, on cases generated from the types (grant tables, session tables, tokens, paths) and on the examples, with the contract's own formula as the property (see Proven, tested, assumed).

    examples/auth/src/main/scala/auth/SessionStore.scala
    final class SessionStore(grantTable: Set[Grant], tokens: String => Option[UserId]):
  def decide(token: String, path: Path): Option[UserId] =
    tokens(token).filter(u => grantTable.contains(Grant(u, path)))

    Code Lean proves is written with terms instead: a define runs as Scala and prints as a Lean definition, and Lean proves it meets its contract (impl). The CRM's SharesExpire is met that way:

    val expireCode = define { (s: Term[CrmStore], now: Term[BigInt]) =>
  CrmStore(s.records, s.shares.filter(sh => !ended(sh, s, now)), s.expiries.filter(e => !ended(Share(e.record, e.to), s, now)))
}

    8. The knowledge base and its command line

    A design decision governs files no proof covers. The knowledge base lists the nodes and attaches the code; here the production class SessionStore runs, tested against DecisionContract.

    val inMemorySessions = Node.design(
  "InMemorySessions",
  "Sessions and grants are loaded into memory, in one process that decides every request.",
  why = "One service decides access, and the tables fit in memory. A shared store would only be needed with several instances."
)("src/main/scala/auth/Server.scala").under(decisionContract)

val knowledge = KnowledgeBase("Auth", idea = "IDEA.md")(
  accessExactly,
  identities,
  grantTable,
  sessionTable,
  requests,
  tokenNamesHolder,
  accessNeedsGrant,
  grantLetsIn,
  decisionContract,
  inMemorySessions
).implement(decisionContract)(SessionStore(grants.value.toSet, sessions.value).decide)

object authCli extends frflow.cli.FrFlowApp(knowledge, root = "examples/auth", extensions = List(frflow.agent.Agent))

    Production calls the operation through service, which checks every result against the contract:

    examples/auth/src/main/scala/auth/Server.scala
    def service(grantTable: List[Grant], tokens: Map[String, UserId]): (String, Path) => Option[UserId] =
  knowledge.service(decisionContract)(grants.bind(grantTable), sessions.bind(t => tokens.get(t)))

    How-to guides How-to

    Each guide is one task. They assume you have run Get started.

    Start a project

    1. Run sbt "frflowInit library", then sbt reload. It creates examples/library with an empty knowledge base and its command line, and adds lazy val library = example("library", layers = Nil) to build.sbt. bin/frflow library status works from here.
    2. Write examples/library/IDEA.md: a title, a lead paragraph, and a section per part of the purpose.
    3. Accept it: bin/frflow library accept IDEA --reason "…", or in review or the web view.
    4. Write the root and its parts, each naming the section of IDEA.md it comes from (idea = "…"), and decide them as in Review a change.

    If IDEA.md changes later, it comes back to you, and so do the nodes that name a changed section. To start with an agent instead, see Start a project with the agent.

    Split a claim into parts

    1. Write each part as a Node.claim (or a contract, or an assumption) with one sentence, a why, and a formula that says exactly that sentence.
    2. Attach it with .under(parent). Edges point up, so the parent's code does not change.
    3. Aim for 2 to 5 parts. Split the root first into what must never happen and what users can do (keycloak's NoUnauthorizedAccess and SignedInAreAccepted), or into state and reads.
    4. Run check. If complete stays open, a part is missing or too weak; see Troubleshooting.
    The keycloak root and its safety half (examples/keycloak/…/Access.scala)
    val realmAccess = Node.claim("RealmAccess",
  "A realm's application accepts a token as a user's, with the user's roles, exactly when the user signed in to that realm and got the token, has not signed out with it since, and is still enabled.",
  why = "The idea in one sentence: applications never see passwords, they ask the server whose a token is. Both halves matter: a token must never let anyone else in (no unauthorized access), and a user who signed in must be let in, or a server that accepts nothing would do."
)(forall((r: Term[Realm.T], t: Term[Token.T]) => forall((u: Term[User.T]) =>
  (accepted(r, t) === some((u, rolesOf(r, u)))) === (signedIn(r, u, t) && enabled(r, u)))))

val noUnauthorizedAccess = Node.claim("NoUnauthorizedAccess",
  "A token is accepted only as a user who signed in to that realm with it, has not signed out since and is still enabled, and only with that user's roles.",
  why = "The safety half of the purpose: whatever an application is told about a token must be true of a sign-in that still stands.",
  idea = "No unauthorized access"
)(forall((r: Term[Realm.T], t: Term[Token.T]) => accepted(r, t).forall(a => signedIn(r, a._1, t) && enabled(r, a._1) && a._2 === rolesOf(r, a._1))))
  .under(realmAccess)

    Define a domain term

    Fix an open type with Opaque := of[T] and an open term with param := expression, inside a Node.definition. A definition is decided, not proven. Two definitions of one term are alternatives: you choose one. See the tutorial's step 4.

    Answer a failing case or a coverage finding

    status and show say what the tests of plain code found. Never change the contract to make a test pass: a changed contract is a decision you review like any other.

    It saysDo
    its code fails a generated case: … ⇒ … given …: whyThe case is already shrunk. Add it as an expect or reject example, fix the code, and run check: the case is tried first until it passes (.frflow/counterexamples.json).
    its code's tests never reached a part of the contract: <part>No generated case made that premise, branch or case hold. Add an example that reaches it, or give a generator for the type that makes such values: .generating(gen.describedAs("…")).
    a generated run differs from the model: on <Impl>, from <state>: <calls>The implementation of a boundary does not do what its model says after those calls. Fix the implementation, or, if the model is wrong, change it: a decision.

    Keep a rule across every operation

    An invariant is a rule over pairs that every contract in its scope keeps (.keeps) or is exempt from, with a reason (.exempt). A new endpoint then has to keep it or say why not.

    examples/keycloak/…/Introspection.scala
    val realmIsolation = Node.invariant[RealmId, Claims]("RealmIsolation",
  "No application is ever shown claims of a realm other than its own.",
  why = "The idea says a token is only ever good in the realm that issued it. Stated once over every answer the server gives, so a new endpoint (user info, an admin view of sessions) must keep it or say why not.",
  idea = "Realms"
)((asking, c) => c.realm === asking)
  .under(onlyTheSignedIn)

    On the contract Introspect, the result shows the rule each claim it returns: .keeps(realmIsolation)((realm, token, res) => res.fold(List.empty[(RealmId, Claims)])(c => List((realm, c)))).

    State what the outside does

    A database or a clock cannot be proven. State what it is trusted to do as an assumption on its operation; the code that calls it is proven from that promise, and checkedBy gives a cheap check run where the code runs. Code that takes several steps against the outside (load, store, log) is a flow over a boundary instead: see Effectful code.

    val sessionLookup = Node.assumption(lookup)("SessionLookup",
  "The store's index returns a session it holds under the token in the realm asked, if it holds one, and never one of another realm or token.",
  why = "Sessions live in a store indexed by realm and token (in memory here; a database or cache in a cluster). Introspection is proven from this promise, not from the index; the index is checked against the define it is decided with on its examples, and every session it returns is checked to be of the realm and token asked."
)((realm, token, r) => r.forall(x => sessions(realm).contains(x) && x.token === token && x.realm === realm) &&
  (sessions(realm).exists(x => x.token === token) ==> r.isDefined))
  .checkedBy((realm, token, r) => r.forall(x => x.token === token && x.realm === realm))

    Review a change

    1. Run bin/frflow PROJECT inbox to see what waits for you.
    2. Run bin/frflow PROJECT review. It shows each node with its diff, parents first. Press a to accept, r to reject, s to skip, v to view the node, q to quit. A layer on top may offer a key of its own (the agent layer's ?).
    3. Or decide one node: accept NODE --reason "…", or reject NODE --reason "…". A reason of a word or two is refused.
    4. For decisions in a browser, run sbt "PROJECT/serve --as NAME" and open the printed link.

    Prove a split by hand

    1. Run bin/frflow PROJECT scaffold NODE. It writes lean/Proofs/<KB>/<Node>.lean with a stub per open obligation.
    2. Use the names frflow_intro gives (h_<Part> for each part), so the proof survives a part being added.
    3. Iterate in lean/ with lake env lean Proofs/<KB>/<Node>.lean, then run check. A proof file may not use sorry or axiom.

    Gate CI on FrFlow

    Commit the Scala, IDEA.md, .frflow/ and lean/Proofs. In CI, run bin/frflow PROJECT ci: it checks, then exits 1 unless every node is proven and decided. Cache .frflow/checks.json and lean/.lake by branch, so only what changed is proven again.

    Domain types

    Case classes and Scala 3 enums are the domain's types; FrFlow derives their Lean structure or inductive. To build one from terms in a formula, give it a companion that extends Data:

    examples/crm/…/Crm.scala
    final case class CrmStore(records: List[CrmRecord], shares: List[Share], expiries: List[Expiry])
object CrmStore extends Data[CrmStore]

enum Change:
  case Add(record: CrmRecord)
  case ShareWith(record: BigInt, to: TenantId, until: Option[BigInt])
  case Unshare(record: BigInt, to: TenantId)
object Change extends Data[Change]

final case class WriteCmd(by: Account, change: Change)
object WriteCmd extends Data[WriteCmd]

/** What changes the store: a user's write, or a run of the expiry job at a time. */
enum Event:
  case Wrote(cmd: WriteCmd)
  case Expired(now: BigInt)
object Event extends Data[Event]
    • A case class is built as CrmStore(a, b, c) on terms (1 to 6 fields); the same call on values still builds a value.
    • An enum case is built through the enum's companion: Event[Event.Wrote](w) (up to 4 fields).
    • of[T] is a type's Lean translation, used in definitions: User := of[UserId].
    • Not supported: recursive types, function-typed fields, and types that redefine equals.

    A define built from these, with a match on an enum and a constructor on terms:

    val matches = define { (q: Term[Search], r: Term[CrmRecord]) =>
  q.on[Search.ById](id => r.id === id)
    .on[Search.OfKind](k => r.kind === k)
    .on[Search.Everything.type](True)
}

val aboutRecord = define { (s: Term[CrmStore], id: Term[BigInt]) =>
  CrmStore(s.records.filter(r => r.id === id), s.shares.filter(sh => sh.record === id), s.expiries.filter(e => e.record === id))
}

    An operation takes 0 to 6 inputs. The post, checkedBy, a keeps view, each expect and reject, and implement take them in order, then the result (a flow's, then the worlds before and after): Node.contract(share)(…)((by, doc, withWhom, result) => …), expect(ann, readme, bob, true, "the owner shares"), implement(share)((by, doc, withWhom) => …).

    Edges and extras:

    • .under(parents*): a part of each parent. Declare parents first.
    • .replaces(other): an alternative; accepting one rejects the other.
    • .keeps(invariant)(view) and .exempt(invariant, reason).
    • .examples(bindings*)(expect(…), reject(…)): every contract needs at least one of each.
    • .checkedBy((a, b, r) => …): a cheaper check run where the code runs, proven to follow from the post.
    • .checkedAtRunTime(RunCheck.Sampled(100)) (or EveryCall, Never): how often service checks the code's results, instead of the default: every call for plain code and outside adapters, none for a proven define that is the running code. A decision, shown in show. A failed check is reported (knowledge.reporting(v => …); a log line by default) before ContractViolation is thrown, which an application maps to its own failure (an HTTP 500).
    • .expects(statement)(formula): a consequence you expect, proven from the node.

    Commands

    bin/frflow PROJECT COMMAND, or sbt "PROJECT/run COMMAND". The full help:

    Output of --help, in a project with no layer on top
    Usage: auth [--plain] COMMAND [ARGS]...

FrFlow: one root refined by a DAG of small statements, each proven in Lean from its parts and decided by the developer.

The developer writes IDEA.md (what the system is for) and accepts it; the root and its parts follow, as Scala, each
decided in turn. Read with tree, show, diff, inbox, find; decide with review, accept, reject, confirm, revisit, gone;
prove with render, check, status, ci, scaffold. The web view does the same in a browser: sbt "PROJECT/serve --as NAME".
Exit codes: 0 fine; 1 something is not accepted or proven, or a decision was refused; 2 a usage error; 3 no Lean (lake).

    What Lean proves

    For each node N with parts C1…Cn, over the open terms they mention, with the definitions in force applied:

    ObligationStatementFails when
    completeC1 → … → Cn → Nnot proven: the parts do not make N
    needed_C, triedN without CLean proves it: C is not needed
    vacuous (one part), triedN, with no hypothesisLean proves it: N says nothing its part adds
    restates, triedN says what its part, or one conjunct, saysLean proves it: a warning
    clash, unsat, triedthe parts imply False; no world meets NLean proves it
    idle (the root), triedthe root holds when every operation does nothingLean proves it: the root does not say what users can do
    implthe attached define meets the contract, from the promises of what it callsnot proven
    root_implthe root holds of the code, from the trusted assumptions alonenot proven
    eval_i, probe_jan example, or an input near one, gives in Lean what it gives in ScalaLean and Scala disagree: FrFlow's Lean printer or evaluator is wrong

    A try is one-sided: shown means Lean proved it; not-shown means it found no proof within a small budget, which shows nothing.

    Proven, tested, assumed Explanation

    The code under a contract, or behind a boundary, is in one of three states. status, show and the web view keep them apart.

    StateThe codeHow it is shown to do what is decided
    provena define or a flow, written with termsLean proves it meets its contract (impl)
    testedplain Scala: a function, or the project's own implementation of a boundaryFrFlow tests it against its contract, or the boundary's model, on generated cases
    assumedan outside system (a database), or an assumption on an operationyou decide it; it is checked at run time, on the examples and on generated runs

    Lean proves everything above tested and assumed code from the contract or the model alone, and root_impl names what it rests on. The tests are built from what you decided:

    • The property is the contract's formula. The term tree Lean reads is evaluated in Scala on each case's inputs and the code's result, with the contract's check and the invariants it keeps. No property is written by hand.
    • The cases come from the types. Generators are derived from case classes, enums, lists, options, maps, sets, numbers and opaque terms (through the definition in force), and the world is generated too: the parameters the contract reads. The examples' values are seeds.
    • Coverage is measured on the formula. Each implication's premise, each side of an ||, each branch and each case of a match must hold in some case; a part no case reached is a finding, so a test cannot pass without reaching the contract.
    • Failures are shrunk to their smallest, kept in .frflow/counterexamples.json and tried first on every later run.
    • Generators you give (.generating(…)) are described beside the results, and share the cases with the derived ones; the examples' values they never make stay seeds. For an outside system's types, they say what the outside can hold, and are all those values are drawn from.

    For the auth example, bin/frflow auth show DecisionContract prints:

    Code
  plain code, tested against the contract, not proven
    SessionStore(grants.value.toSet, sessions.value).decide
  tested: 1,000 generated cases (seed 1), against DecisionContract
    every case meets it, and every part of it was reached

    A service of the project's own implements a boundary's trait and is tested against the boundary's state model: generated runs (a state, then 1 to 12 calls with generated arguments) are run on the implementation and on the model, and every result and the state read back after each call must be the model's. A failing run is shrunk to the fewest, smallest calls. With a store that keeps a record's old shares, the CRM's run is reported as on LeakyDatabase, from Tables(CrmStore(List(), List(Share(0, TenantId(""))), List()), List()): storeAbout(0, CrmStore(List(), List(), List())): it still holds the share, where the model holds none. An outside system given with .checkedAgainst goes through the same runs (at most 200), and its model stays assumed.

    Seeds. Runs are seeded: .testedWith(TestSettings(cases = 1000, seed = 1)). A CI job runs ci twice, with the fixed seed and with FRFLOW_SEED=fresh, so a case the fixed seed never makes can still be found.

    Effectful code: flows over boundaries Explanation

    Code that takes several steps against the outside (load from a database, store, log) is written as a flow, in the style of Cats Effect or ZIO code. Its order and its loops are then proven, not only reviewed. A single call whose result is checked can stay an assumption on an operation (State what the outside does).

    • Flow[A] is FrFlow's monad, written with for, <- and yield. It is printed as a Lean do block over any monad with the boundaries' operations, and runs in any cats.effect.Sync.
    • A boundary is a trait whose operations take terms and return flows: what proven code calls but cannot see. The model names one value for it, Boundary[T].
    • A state model says what a boundary does: another implementation of the same trait, over a state, written with state.get, state.set and state.update. You decide it as an assumption; in Lean it is an instance on StateM.
    • A flow's contract relates the input and the result to the boundaries' states before and after the run. Lean proves the attached flow meets it, on the models.
    • Time is the Clock boundary: Flow.now, Flow.sleep(d), Flow.waitUntil(t), f.timeout(d) (an Option, no cancellation) and Flow.every(period)(job). Its model holds the time and the delays a sleep may add, so a flow is proven for every start and every late wake-up; a fake clock is tested against it. Deadlines are claims over runs of events, proven by induction (FrFlow.always_when) under the scheduler's assumption. See examples/sharing.

    A boundary and its model

    examples/crm/…/Database.scala
    /** What proven code may ask of the database. */
trait Database:
  /** The records, shares and expiries it holds. */
  def load: Flow[CrmStore]
  /** Holds what `t` holds about the record `id` in place of what it held about it. */
  def storeAbout(id: Term[BigInt], t: Term[CrmStore]): Flow[Unit]
  /** Appends an event to the event log. */
  def logEvent(e: Term[Event]): Flow[Unit]

val db = Boundary[Database]("database", "the SQLite database the CRM keeps its records, shares, expiries and event log in")

/** What the database holds: the store, and the event log. */
final case class Tables(store: CrmStore, events: List[Event])
object Tables extends Data[Tables]

/** The database as the proofs see it. */
object DatabaseModel extends Database, StateModel[Tables]:
  def load = state.get.map(t => t.store)
  def storeAbout(id: Term[BigInt], s: Term[CrmStore]) = state.update(t => Tables(replaceAbout(t.store, id, aboutRecord(s, id)), t.events))
  def logEvent(e: Term[Event]) = state.update(t => Tables(t.store, t.events ++ List(e)))

val tablesModel = Node.assumption(db)(DatabaseModel)("TablesModel",
  "The database holds a store and an event log: it gives the store as it holds it, holds the rows a store has about a record in place of those it held about it, leaving the other records' rows, and appends an event to the log.",
  why = "…",
  idea = "Expiring shares")
  .checkedAgainst(t => SqliteDatabase.holding(t), _.tables)
  .implementedBy(t => MemoryDatabase.holding(t), _.tables)

    The model's node names the boundary's implementations: start makes one holding a model's state, read reads its state back. SQLite is an outside system (.checkedAgainst): the model stays assumed, and SQLite is checked against it on the examples of the flows that call it and on generated runs. MemoryDatabase, the CRM's in-memory store for development and tests, is the project's own code (.implementedBy): it is tested against the model on generated runs (Proven, tested, assumed). An implementation builds its operations with Flow.effect:

    examples/crm/…/Database.scala
    final class SqliteDatabase(sql: Db) extends Database:
  /** What it holds, read back. */
  def tables: Tables = Tables(sql.load(), sql.events())
  def load = Flow.effect(sql.load())
  def storeAbout(id: Term[BigInt], t: Term[CrmStore]) = Flow.effect(id, t)((i, s) => { sql.storeAbout(i, s); () })
  def logEvent(e: Term[Event]) = Flow.effect(e)(sql.logEvent)

    A flow and its contract

    The flow calls the operation expire (SharesExpire's), so it is proven from that contract, not from its code.

    examples/crm/…/Job.scala
    def expireOnce(now: Term[BigInt]): Flow[CrmStore] =
  for
    s <- db.load
    t  = expire(s, now)
    _ <- changedIds(s, t).traverse_(id => db.storeAbout(id, t))
    _ <- db.logEvent(Event[Event.Expired](now))
  yield t

    The contract is on an operation whose type is a flow, Param[A => Flow[R]]. Its post takes the inputs, the result and the worlds before and after; before(DatabaseModel) is the database's state before the run. Its examples give a world before, the result, and the world after:

    examples/crm/…/Expiry.scala
    val runExpiry = Param[BigInt => Flow[CrmStore]]("runExpiry",
  "a run of the expiry job at a time (in seconds), on the database: the store it computes; the database holds it after")

val expiryJob = Node.contract(runExpiry)("ExpiryJob",
  "A run of the expiry job at a time leaves the database holding, about each record, what SharesExpire's run on what it held gives, logs the run at the end of the event log, and returns that store.",
  why = "…",
  idea = "Expiring shares"
)((now, result, before, after) =>
  sameRows(after(DatabaseModel).store, expire(before(DatabaseModel).store, now)) &&
    after(DatabaseModel).events === before(DatabaseModel).events ++ List(Event[Event.Expired](now)) &&
    result === expire(before(DatabaseModel).store, now))
  .examples()(
    expect(BigInt(150), World(DatabaseModel -> Tables(globexUntil100, earlier)), initechOnly,
      World(DatabaseModel -> Tables(initechOnly, earlier :+ Event.Expired(150))), "Globex's share ended at 100: the database drops it, and the run is logged"),
    …)

    It is attached as other proven code is, with .implementProven(expiryJob)(expireOnce). A contract on a flow may have no parent: production runs it, as an entry point. A design node under it says when it runs and how it has the database to itself (in the CRM, every minute, under the database's lock).

    Running it

    examples/crm/…/Job.scala
    def runExpiryJob(d: Db, now: BigInt): CrmStore = d.synchronized {
  knowledge.run[SyncIO](expiryJob)(db.bind(SqliteDatabase(d)))(now).unsafeRunSync()
}

    knowledge.run[F](contract)(bindings*) runs the proven flow in F, calling the bound implementations of its boundaries. The CRM runs it in SyncIO on the thread that holds the lock; IO works too where nothing else needs the lock.

    In Lean

    The boundary becomes a class, the model a def per operation in StateM, and the flow a generic do block:

    Generated: lean/FrFlowGen/Crm/Domain/Def_expireOnce.lean
    @[frflow_defs] def expireOnce {m : Type → Type} [Monad m] [Database m] (expire : CrmStore → Int → CrmStore) : Int → m CrmStore :=
  fun (now : Int) => do
    let s ← Database.load
    let t := (expire s now)
    for id_ in (Crm.changedIds s t) do
      Database.storeAbout id_ t
    Database.logEvent (Event.Expired now)
    pure t

    impl states the contract of expireOnce_run, the flow run on the models (FrFlow.runOn over StateM World), given SharesExpire's promise. To prove it by hand, simp only with the run lemmas (FrFlow.runOn_bind, runOn_pure, runOn_within, runOn_get, runOn_modify, runOn_forIn_unit), the generated Database.<op>_onWorld lemmas and the model's definitions, keeping the domain's definitions folded. runOn_forIn_unit turns a loop into a List.foldl over worlds; what the fold does is then proven by induction on the list. The CRM's proof is examples/crm/lean/Proofs/Crm/ExpiryJob.lean.

    What a state model assumes

    • Deterministic. Each operation has one outcome. What is unknown, such as a clock's readings, goes into the state; the proofs hold for every start state.
    • Failures as faults. A boundary declared failing may fail at any call, changing nothing; the world's faults say which calls fail, and a proof holds for every pattern of them.
    • Exclusive, or one step. Nothing else changes the state between two steps of a transaction (Flow.atomically), which Lean reads as one step; a design node says how that is ensured (in one process, FrFlow's lock). Branches at once (parTupled, parTraverse) are read in turn, with the proof that whole branches commute (commute_i); their steps interleaved are tested, not proven.
    • Loops over lists. A flow loops with xs.traverse_(x => …), so it terminates.

    Steps of the outside world (Flow.effect) belong to production implementations only: a proven flow that takes one is refused when the knowledge base is rendered.

    How decisions and review work Explanation

    You decide every node, once. Whoever writes a node proposes it, with a why and examples; only a decision signed with your key accepts it. A decision binds your reason to the hash of what you saw, so whatever moves under it puts the node back up for review, with the cause:

    CauseWhat moved
    selfwhat the node says: statement, formula, why, examples, terms, its code
    abovethe meaning of a parent, of a definition it uses, or of a contract its code calls
    partsits list of parts
    codethe files it governs
    revisityou asked to see it again
    mergedtwo branches decided it

    Rewording a statement whose formula is unchanged reviews only that node; a change of formula reviews what rests on it. A node under review whose own content did not change and that Lean proves again is mechanical: confirm accepts all of them in one decision. Your key is kept outside the repository, where neither a script nor an agent editing it can sign as you.

    What is trusted, and the limits Explanation

    Lean proves the nodes consistent with each other and the root of the code. You decide that they are the right theory. Trusted:

    • the assumptions you accept, which are the hypotheses of root_impl, checked where they can be;
    • that a term means in Lean what it computes in Scala. Both come from one tree, and the examples and probes near them are evaluated in both and compared;
    • tested code: plain Scala under a contract and the project's own implementations of a boundary, tested on generated cases, not proven. The tests say which parts of the contract or the model they never reached;
    • the state models of boundaries: that an outside system behaves as its model, checked on the examples and on generated runs where .checkedAgainst is given;
    • that parameters hold the data they are said to mean, and that every path to the data goes through service or a proven flow: design nodes are reviewed, not proven;
    • your signing key.

    Limits: the tries are one-sided; testing covers the examples and the generated cases, not every input; ordering, liveness, failures of the outside world and concurrent access to a boundary are not covered; maps and sets cannot be iterated.

    With an AI agent How-to

    The agent layer (modules/agent, package frflow.agent) is on top of FrFlow's core, which does not depend on it. It adds what an agent working in the project needs: its commands, your requests to it, the conversation IDEA.md comes from, and their parts of inbox, show, review, status and the web view. The agent's rules are in .claude/skills/frflow/SKILL.md.

    Enable it

    Name it on the project's main object; example("NAME") in build.sbt depends on the module (example("NAME", layers = Nil) does not). The three examples enable it.

    object authCli extends frflow.cli.FrFlowApp(knowledge, root = "examples/auth", extensions = List(frflow.agent.Agent))

    The layer is an Extension of the core's: a CliExtension (its commands, and what it adds to a view) and a WebExtension (its routes, and a script that hooks into the page with FrFlow.extend). Another layer is written the same way.

    Start a project with the agent

    1. Run sbt "frflowInitAgent library", then sbt reload: as frflowInit, with the agent layer enabled.
    2. Tell the agent your idea in chat, in your own words. It records them (said).
    3. Answer its questions. It asks three to five at a time, each with the answer it assumes, so you can agree or correct it. It records each question (asked, numbered Q1, Q2, …) and your answer (replied). bin/frflow library conversation shows what is recorded; inbox lists the questions not answered yet.
    4. Confirm the purpose in one sentence when the agent restates it: it becomes the root.
    5. Read IDEA.md, which the agent writes from the conversation (each section names the answers it comes from on a From: line), and accept it: accept IDEA --reason "…", or in review or the web view. To change it, tell the agent.
    6. The agent proposes the root and its parts; decide them as in Review a change.

    The conversation is a record the agent keeps in .frflow/conversation.json, not a decision: only IDEA.md and the nodes are signed. A changed answer is a warning in status until you look at IDEA.md again and accept it.

    Ask the agent for a change

    • ask NODE TEXT, or ask --idea TEXT; in review, ? on a node; in the web view, on the node or on IDEA.md. The node waits with the agent, out of your queue, until it answers or changes the node.
    • The agent's answers are in inbox; close REQUEST when you have read one.
    • A node you reject, and one you ask to revisit, are listed in inbox for the agent.
