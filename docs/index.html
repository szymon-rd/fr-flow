    FrFlow documentation

    This page describes an earlier design. Its tutorial and how-to guides are written with programs (Flow), state models and the clock, which FrFlow no longer has: a service's state is now a structure, a trait with a class that implements it. The current API is in README.md and USAGE.md; the examples under examples/ (payments, rooms, auth, shop) are written with it.

    FrFlow is a method and a tool for building software with AI agents without losing track of what the software is for. A small set of root statements is refined by a graph of small statements down to the code. Lean proves that each step holds, that the statements do not contradict each other, and that the code meets them. You decide every statement, and you see it again when it changes.

    FrFlow is written in Scala 3 and uses Lean 4. This page has four kinds of section, marked next to each heading: a tutorial to learn it, how-to guides for tasks, the reference, and explanations of why it works as it does. For an overview, read the README; the full reference is docs/USAGE.md.

    FrFlow is in two layers. FrFlow (core), every section up to With an AI agent, is the method and its tools: the graph, the proofs, the decisions, the CLI and the web view, which a developer uses with no AI. With an AI agent is a layer on top, which a project enables: an agent proposes the nodes and writes the code and proofs, and the developer asks it for changes.

    Why FrFlow Explanation

    When agents write the code, nobody on the team builds the theory of the program: why it is built the way it is, and how it maps to the world. A codebase that grows without that theory drifts from what it is for. FrFlow keeps the theory as code beside the code: a few root statements, refined step by step (stepwise refinement, Wirth 1971; the refinement calculus, Back 1978 and Morgan 1990) down to the code that meets them.

    • Every step is a proof. A statement's parts, with the assumptions it lists, imply it; Lean checks it. Proven code is proven against its statements; plain Scala is tested against them on generated cases.
    • The statements are consistent. Lean proves that some meaning of every abstract concept makes them all hold; without that proof the model is red.
    • The developer decides. Every statement is accepted with a signed decision and a reason, and comes back for review, with the diff, when anything it rests on changes. An agent cannot sign.

    Nothing is checked when the code runs: FrFlow is for testing before production, and for proofs.

    Get started Tutorial

    You need JDK 17 or later, sbt, and Lean 4.35.0 installed with elan, so that lake is on the PATH. From a clone of the repository:

    sbt "frflowInit toy --as NAME"     # examples/toy: an empty FrModel, its main object, its examples' class
sbt reload
bin/frflow toy status
sbt "toy/serve --as NAME"          # the web view on localhost

    --as NAME lists your key as the project's first decider (.frflow/deciders, signed by it): commit it. The examples FrFlow ships are projects in examples/<name> (rooms, auth, payments, shop): bin/frflow rooms status. FrFlow's own suites check each whole: sbt leanTest.

    Tutorial: read a FrModel, top to bottom Tutorial

    The rooms example: people book meeting rooms for a stretch of time, and a room holds one meeting at a time. Its whole source is in examples/rooms.

    1. The domain

    Domain types are case classes deriving LeanType. A define is a Definition given its meaning on the spot: a Lean def, and Scala the evaluator runs.

    final case class Booking(room: String, start: BigInt, end: BigInt) derives LeanType
final case class RoomBookings(room: String, bookings: List[Booking]) derives LeanType

val covers = define { (b: Term[Booking], t: Term[BigInt]) => b.start <= t && t < b.end }

val apart = define { (a: Term[Booking], b: Term[Booking]) =>
  a.room =!= b.room || forall((t: Term[BigInt]) => !(covers(a, t) && covers(b, t))) }

val free = define { (bookings: Term[List[Booking]], request: Term[Booking]) =>
  bookings.forall(b => apart(b, request)) }

    2. The roots, over Declarations

    The purpose is stated over Declarations: concepts known only by what the statements say of them. A statement holds in every state the service reaches and reads what changes, such as what is booked, in the current one. What comes from the booking form is trusted, so it is an assumption, stated with always: every value of the type that can occur.

    val booked = Declaration[List[Booking]]("the bookings made, as the world stands")
val bookedAfter = Declaration[Booking => List[Booking]]("the bookings made once a request is handled")
val accepted = Declaration[Booking => Boolean]("whether a request is accepted")

val bookingsEndAfterStart = Node.assumption("Every booking ends after it starts.")(
  always[Booking](b => b.start < b.end))

val bookWhenFree = Node.claim("A request is booked exactly when its room is free for its whole time.")(
  forall((request: Term[Booking]) =>
    bookedAfter(request) === when(free(booked, request))(booked :+ request).otherwise(booked)))
  .assuming(bookingsEndAfterStart)

val acceptWhenFree = Node.claim("A request is accepted exactly when its room is free for its whole time.")(
  forall((request: Term[Booking]) => accepted(request) === free(booked, request)))
  .assuming(bookingsEndAfterStart)

    3. The program and the table's model

    Booking is a Definition whose code is a program: a Flow, written as a for comprehension, run in one transaction. The table's two operations are Definitions too, given their meaning in Lean by a StateModel.

    val book = Definition[Booking => Flow[Boolean]]("booking a request: whether it was booked")
val inRoom = Definition[String => Flow[RoomBookings]]("a room's bookings, as the SQLite table gives them")
val add = Definition[Booking => Flow[Unit]]("a booking added to the SQLite table")

object storedBookings extends StateModel[List[Booking]]("every booking stored, oldest first"):
  inRoom.means(room => state.get.map(stored => make[RoomBookings](room, stored.filter(b => b.room === room))))
  add.means(booking => state.update(stored => stored :+ booking))

val bookIfGranted = program { (request: Term[Booking]) =>
  (for
    held  <- inRoom(request.room)
    booked = granted(held, request)
    _     <- Flow.when(booked)(add(request))
  yield booked).atomically }

    4. The world outside, and what always holds

    What the world does with the table is assumed of its model; a claim of always about its state is a rule below the roots, which Lean proves every program writing the table keeps.

    val nothingElseWrites = Node.assumption("Nothing but the booking code changes the table.")(
  storedBookings.onlyCodeChanges)
val startsEmpty = Node.assumption("The table starts empty.")(storedBookings.initially(stored => stored === Nil))
val oneAtATime = Node.assumption("Bookings are processed one at a time.")(storedBookings.atomic)

val neverOverlap = Node.claim("The bookings stored never overlap.")(
  always(storedBookings)(stored => stored.pairwise(apart)))
  .refines(bookWhenFree, acceptWhenFree)
  .assuming(nothingElseWrites, oneAtATime, startsEmpty, bookingsEndAfterStart)

    5. What each Declaration is, in the code

    A program applied in a statement is a run from the current world: .result is what it returns, .after the world it leaves, read with storedBookings.in(…); beside a run, .current names the world before it.

    val acceptedIsAnswered = Node.claim("A request is accepted exactly when booking it answers booked.")(
  forall((request: Term[Booking]) => accepted(request).current === book(request).result))
  .refines(acceptWhenFree)

val bookedAfterIsStored =
  Node.claim("What is booked once a request is handled is what the table holds after booking it.")(
    forall((request: Term[Booking]) => bookedAfter(request).current === storedBookings.in(book(request).after)))
  .refines(bookWhenFree)

    Below them, claims about booking's code, proven of the program in Lean:

    val storeWhenFree = Node.claim("A request is stored exactly when its room is free for its whole time.")(
  forall((request: Term[Booking]) =>
    val stored = storedBookings.current
    storedBookings.in(book(request).after) === when(free(stored, request))(stored :+ request).otherwise(stored)))
  .refines(bookWhenFree)
  .assuming(oneAtATime, bookingsEndAfterStart)

    6. The calendar, tested

    The calendar is plain Scala, not proven: FrFlow tests it against its claim on generated cases, each drawn meeting the rules on its type. Lean proves the step from its claim over start and end times to the one over moments.

    val granted = Definition[(RoomBookings, Booking) => Boolean]("whether a request is granted, given its room's bookings")

val noOverlap = define { (a: Term[Booking], b: Term[Booking]) =>
  a.room =!= b.room || a.end <= b.start || b.end <= a.start }

val grantWhenNoOverlap = Node.claim("A request is granted exactly when it overlaps no booking of its room.")(
  forall((held: Term[RoomBookings], request: Term[Booking]) =>
    granted(held, request) === held.bookings.forall(b => noOverlap(b, request))))
  .refines(grantWhenFree)
  .assuming(bookingsEndAfterStart)

    7. The FrModel and its examples

    The FrModel lists the nodes and gives each Definition its meaning; examples are ordinary tests.

    val rooms = FrModel("Rooms")(bookWhenFree, acceptWhenFree, bookedIsStored, bookedAfterIsStored, acceptedIsAnswered,
  storeWhenFree, answerWhenFree, neverOverlap, grantWhenFree, bookingsOfTheRoom, roomBookingsApart, grantWhenNoOverlap,
  nothingElseWrites, oneAtATime, startsEmpty, bookingsEndAfterStart)
  .implementProven(book)(bookIfGranted)
  .implementTested(granted)(_ => (held, request) => Calendar(held).grants(request))
  .implementTested(inRoom, add)(start = BookingsTable.holding, observe = _.bookings)(t => (t.inRoom, t.add))
  .withGenerator(roomNames.describedAs("Oak or Elm"))
  .withGenerator(requests.describedAs("requests for Oak or Elm that end after they start"))
  .withGenerator(roomBookings.describedAs("a room's bookings, laid end to end, some back to back"))

class GrantedExamples extends FrFlowExamples(rooms):
  example("back to back: granted"):
    granted(RoomBookings("Oak", List(Booking("Oak", 9, 10))), Booking("Oak", 10, 11)) is true

    check proves the steps, tests the code and has Lean prove the statements consistent:

  bookedAfterIsStored, acceptedIsAnswered, grantWhenNoOverlap: proven
    granted: as grantWhenNoOverlap defines it

    accepted: as acceptedIsAnswered defines it

    How-to guides How-to

    Start a project

    1. sbt "frflowInit NAME --as YOU", then sbt reload.
    2. Write the roots in examples/NAME/src/main/scala/NAME/Model.scala: a few claims, each one idea, over Declarations where the purpose is more general than the code. List them in FrModel("Name")(…).
    3. bin/frflow NAME check, then review to decide each node.

    Split a claim into parts

    Write the parts as claims with .refines(parent): together, with the assumptions the parent lists, they must imply it. check proves the step (complete) and that each part is needed. Two to five parts, as a rule; the first split is safety and capability, or state and reads.

    Say what a Declaration is

    At the bottom, a claim relating the Declaration to the code (bookedAfter(request).current === storedBookings.in(book(request).after)) is its meaning: it is not proven of the code, and the code stands in it in its consistency group, which Lean proves.

    Give a Definition its meaning

    • Proven: .implementProven(book)(bookIfGranted), a program or a define.
    • Tested: .implementTested(granted)(env => (held, request) => …), plain Scala.
    • An operation on a state: op.means(…) in its StateModel, and its Scala with .implementTested(ops*)(start = …, observe = …)(t => …).
    • A value: .implementValue(d)(v); given where the code runs: .implementProvided(d).

    Model an outside system known by its promises

    An operation with no meaning of its own is op.assumed in its model; what is promised of it is written as assumptions about its runs. Lean takes them as hypotheses; its Scala is tested against them where a generated run can tell, and is otherwise reported "trusted, not tested".

    val fetch = Definition[(Account, Search) => Flow[List[CrmRecord]]]("the database's answer to a search")

object databaseModel extends StateModel[Tables]("the SQLite database the CRM keeps its records in"):
  load.means(state.get.map(t => t.store))
  fetch.assumed

val searchKeeps = Node.assumption("A search changes nothing the database holds.")(
  forall((user: Term[Account], query: Term[Search]) =>
    databaseModel.in(fetch(user, query).after) === databaseModel.current))

    Write a program that can fail

    Declare the error on the Definition; its .result is then an Either, and a claim about its run covers both outcomes. A model whose calls may fail is StateModel.failing.

    val housekeeping = Definition[Flow[Unit]]("a run of housekeeping").failsWith[Failure]

object libraryModel extends StateModel.failing[Library, Failure]("where the library is kept; it may be down",
    Failure.StoreUnavailable):
  load.means(state.get)
  save.means(library => state.set(library))

    Use the clock

    The clock is FrFlow's model: Clock.now, Clock.sleep(d), and the world's own Clock.elapse(d) between runs. A schedule is a trusted fact restricting how the world moves the time.

    val housekeepingOnTime = Node.assumption("Housekeeping runs at least every two minutes.")(
  Clock.clockModel.schedule(housekeptModel)((now, ran) => now <= ran + 120))

val answered = program { (request: Term[Request]) =>
  serve(request).timeout(Clock.now, 30) }

    Say that a value stays the same

    t.isConstant says no run of any program changes t; under a condition, while it holds.

    val loadedKept = Node.claim("The accounts as loaded at start never change.")(seed.isConstant)

val booksStay = Node.claim("A booking once made is never removed.")(
  forall((b: Term[Booking]) => storedBookings.current.contains(b) implies storedBookings.current.contains(b).isConstant))

    Answer a failing case

    A generated case that fails names the inputs, the seed, the case and its size. Fix the code, or, if the claim as decided is wrong, say so: never weaken a claim to make a test pass. Re-run with the same seed to see it again.

    Review a change

    inbox lists what waits, parents first; review goes through it, diff NODE shows what moved since a node was decided, and confirm accepts the mechanical decisions in one batch.

    Prove a step by hand

    When Lean's tactics do not find a proof, write it in lean/Proofs/<Model>/<node>.lean; scaffold NODE writes a stub for each obligation the last check left open. Lemmas shared by several proofs go in Lemmas.lean.

    a proof file
    -- lean/Proofs/Rooms/grantWhenFree.lean
import FrFlowGen.Rooms.grantWhenFree.Spec

namespace Rooms.grantWhenFree.Proofs

theorem complete : Obl.complete := by
  unfold Obl.complete
  intro granted h
  unfold claim
  ...

    Gate CI on FrFlow

    ci checks, then exits 1 unless everything is proven and decided. Run it a second time with a fresh seed, so a case the fixed seed never makes can still be found:

    bin/frflow NAME ci
FRFLOW_SEED=fresh bin/frflow NAME ci

    Programs

    A program is a Flow[R], written as a for comprehension: .atomically, Flow.when, Flow.cond, Flow.ifM, Flow.each, Flow.collect, Flow.fold, Flow.parCollect, Flow.parCollectN, (fa, fb).parTupled, fa.race(fb), Flow.raise, fa.handle, fa.attempt, fa.guarantee, Flow.bracket, fa.timeout(Clock.now, seconds), Flow.retry(Clock.sleep, waits)(fa). One that can fail declares it on its Definition, .failsWith[E].

    Proven, tested, assumed Explanation

    Proven code is a define or a program: Lean proves the claims about it. Tested code is plain Scala: it is tested against its claims on generated cases, each argument drawn meeting the rules on its type, and a model's operations against the model on generated runs, two calls at once among them. Assumed code is known only by the assumptions about it: Lean takes them as given, and its Scala is tested against them where a run can tell.

    What proven code hands to plain Scala meets the rules on its type: a Lean obligation at each call (made_<code>_call_<i>), since the Scala is tested only on such values. Values from outside are covered by an assumption of always on their type, and every value covered code makes or stores is still proven to meet it.

    The World, programs and time Explanation

    A World is the application at one moment, as the proofs see it: one field per model's state. Code never sees it; in production the real systems are the state. A statement holds in every world the service reaches and reads what changes in the current one, so a root can speak of "what is booked" without naming a store, and adding a store brings back no statement that does not read it.

    A program's steps are recorded once. Lean reads them as a do block run on the models; the Scala tests run them on the models, and on the implementations interleaved; production folds them into Cats Effect. Steps at once are read in turn, and each two that touch a model in common are proven to commute, so what is proven of the reading holds of every interleaving.

    Time is Cats Effect's: the clock is a model, steps of code take no time, and the world moves the time on, between runs (elapse) and at each of the clock's steps; a wait takes at least its seconds, and waits at once the longest of them. Every rule and isConstant reading the clock is proven to survive time passing.

    FrFlow states safety properties: "eventually", and two runs in sequence in one statement, are out of scope.

    How decisions and review work Explanation

    Every node is decided once by the developer, with a reason, signed with a key on the project's committed list of deciders. A decision binds the reason to the hash of what the developer saw: whatever moves under it (what the node says, what it rests on, its parts, its code, a new program changing a store its rule is about) brings it back, with the cause and the diff. Rewording a node whose meaning is unchanged reviews that node only. A node whose own content did not change and that Lean proves again is mechanical: confirm accepts those in one batch.

    What is trusted, and the limits Explanation

    Trusted: the assumptions the developer accepted; FrFlow's translation to Lean, cross-checked by the examples, which run the same model as Scala; for tested code, the cases the tests reach. Lean's kernel checks every proof; generated Lean is never edited, and proof files may hold only what FrFlow allows. Not modelled: liveness, two runs in sequence in one statement, values inside maps, sets or functions under an always[T].

    With an AI agent How-to

    The agent layer (modules/agent) adds the agent's commands, the developer's requests, and the conversation the idea comes from. It proposes and asks; deciding stays the developer's. Its rules are in the frflow skill.

    Enable it

    object toyCli extends frflow.cli.FrFlowApp(frModel, root = "examples/toy", extensions = List(frflow.agent.Agent))

    sbt "frflowInitAgent NAME --as YOU" sets up a new project this way.

    Start a project with the agent

    1. Tell the agent the idea in chat. It asks a few questions at a time, each with the answer it assumes, and records the conversation (said, asked, replied).
    2. It drafts the project's README and proposes the roots and their first parts.
    3. You decide each node, in review or the web view; you ask for changes with ask NODE TEXT.

    The agent layer's commands

    CommandDoes
    ask NODE TEXT, ask --idea TEXT, close REQUEST...the developer asks for a change; closes an answer read
    conversationwhat was said, the questions and the answers
    said TEXT, asked QUESTION --assume ANSWER, replied QUESTION TEXTthe agent records the conversation
    context NODEeverything on a node, with its requests
    answer REQUEST|NODE TEXTthe agent replies

    Its files are .frflow/requests.json and .frflow/conversation.json; the core does not read them.
